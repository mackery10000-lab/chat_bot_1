# 선택지와 자유 입력을 함께 사용하는 대화 규칙

게임의 아이템·장소·출입·장치·엔딩은 계속 서버 엔진이 판정한다.
선택지는 서버 사건의 바로가기이며, 자유 입력도 같은 사건으로 연결할 수 있다.
모델이 생성한 대사나 사용자의 주장으로 진행 조건을 바꾸지 않는다.

## 먼저 적용하는 진행 경계

| 대상 | 필요한 조건 | 단순 대화로 바뀌지 않는 것 |
| --- | --- | --- |
| 탐험가의 신문 | 실종 사건 소개 또는 현재 상황 설명 | 인사·정차 질문만으로 지급하지 않음 |
| 손전등·안내서 | 직접 조사하겠다는 의사 또는 실제 조사 제안 수락 | 가정·거절·다친 발목에 대한 안부는 수락이 아님 |
| 노인의 외형 증언 | 표 외형을 묻는 진행 질문 | 도난 질문으로 외형을 공개하지 않음 |
| 청소원의 승차권 | 노인의 외형 증언 + 같은 표의 두 특징을 한 답변에서 설명 | 여러 부분 답변이나 다른 물건의 특징을 합산하지 않음 |
| 노인의 목적지 기억 | 오래된 표 열람·원본 반환 | 사용자가 역명을 말해도 공개 단계가 열리지 않음 |
| 승무원의 의뢰 | 이상 현상 인정·기관실 진입 필요성·의뢰 제안·실제 수락 | 잡담에 대한 “네”로 이전 의뢰를 수락하지 않음 |
| 승무원실 문 | 안내서 열람 후 화면에서 덮개·레버 조작 | 채팅의 조작 선언으로 문을 열지 않음 |
| 기관실 출입 | 실제 문 개방·보고서 발견·열람 확인·승무원에게 제시 | 보고서 보유만으로 열람을 인정하지 않음 |
| 현재 연도 인정 | 허용된 증거의 전용 최종 확인 | “지금은 2026년”이라는 주장만으로 인정하지 않음 |
| 최종 엔딩 | 전용 확인에서 목적지·비밀번호 판정 | 채팅에서 비밀번호를 말해도 시도를 소비하지 않음 |

정답 목적지는 ‘아지산’ 또는 ‘아지산역’, 비밀번호는 ‘2026’이다.
신문을 독립적인 증거로 인정하는 기존 규칙과 취소·중복 요청 처리도 유지한다.

## 입력의 의미와 답변 종류 분리

`services/dialogue_routing.py`의 `ground_dialogue_route`를 실제 분류기와
서비스 양쪽에서 호출한다. 모델이 현재 선택지와 의미가 같다고 판정한
입력은 해당 서버 사건으로 연결한다. 표현이 다르다는 이유만으로
문자열 일치나 특정 키워드를 다시 요구하지 않는다.

선택지 ID는 현재 인물·단계에서 제시한 목록과 대조한다. 미래 선택지나
다른 장소의 선택지를 실행하지 않는다. 부정·간접 인용·가정·설정 변경
요구는 실제 진행 답변으로 사용하지 않는다. 나이·경력·식사 같은 무관한
질문에 잘못 붙은 선택지 ID도 진행 수락으로 쓰지 않는다.

분류 문맥에는 현재 선택지의 의미와 `answer_expectation`을 제공한다.
이 정보에는 현재 질문의 종류와 기대 주제, 짧은 수락 가능 여부만 들어간다.
앞으로 나올 대사·비공개 정답·아이템 지급 권한은 포함하지 않는다.

잡담을 해도 의뢰나 분실물 설명 상태는 보존한다. 다만 잡담 직후의 “네”는
그 잡담에 대한 답으로 처리한다. “승무원실 문을 열어드리겠습니다”처럼
대상을 분명히 하면 원래 진행 대화로 돌아갈 수 있다.

## 질문에 답하는 인물

- 탐험가의 정차 질문은 정차에 답한다. 사건 소개를 했다면 신문 지급도 같은 턴에 처리한다.
- 노인은 정차 방법을 모른다고 답하고, 표의 도난은 목격하지 않았다고 구별한다.
- 승무원은 이상 현상에 관한 답을 받으면 `why_engine`을 완료하고 다음 단계로 넘어간다.
- 기관사는 연도 증명을 받은 뒤에도 질문 주제를 먼저 처리한다. 목적지·정차·반복·암호 질문을 같은 안내로 덮지 않는다.
- 같은 열차 안에서의 최근 대화는 이어가지만, 오래전 친분이나 첫 대면의 반복 연출은 만들지 않는다.

`public_dialogue_facts`는 현재 인물과 서버 플래그로 승인한 사실만 새 목록으로
복사한다. 자유 대화는 그 사실을 읽고 설명할 수 있지만 아이템 지급·문 개방·
출입 허가·새 해법·엔딩을 주장할 수 없다. 생성 결과가 범위를 벗어나면
현재 질문에 맞는 안전한 응답으로 대체한다.

진단이 필요하면 `services.chatbot_service` 로거의 DEBUG 출력을 사용한다.
라우팅된 인물·의도·주제·선택지 ID만 기록하며 사용자 입력 원문이나
API 키·프롬프트는 로그에 넣지 않는다.

## 검증

```powershell
.\runtime\python.exe -m unittest discover tests
.\runtime\python.exe -X utf8 tools/check_live_scenario.py --suite tools.live_dialogue_parity_cases:run_suite --max-calls 100
```

오프라인 검사는 실제 서버 전이·상태·아이템 이벤트·선택지·확인 화면을 비교한다.
실제 모델 검사는 새 임시 게임에서 체크포인트를 얻은 뒤 표현이 다른 문장과
화면 선택을 섞어 진행한다. 사용자 저장 기록과 `.env`는 변경하지 않는다.
실제 모델 검증은 API 호출을 사용하며 위 명령으로 명시적으로 실행할 때만 동작한다.

## 인물 상호작용 추가 검증

제보된 인사·정차·도난·이상 관찰·순환 원인의 수정과, 서로 다른 자유발화
200개에 대한 실제 API 검수는 [인물 상호작용 검증 기록](DIALOGUE_QA_2026-11-11.md)에
정리한다. 최초 실패 기록과 수정 후 결과를 구분해서 보관한다.

## 앞선 진행 동등성 검증 (2026-11-11)

- 전체 오프라인 테스트 250개 통과. 현재 선택지와 자유 입력의 상태·아이템·
  선택지·확인 UI 동등성, 인물별 공개 범위, 부정·가정·간접 인용을 포함한다.
- 실제 모델로 5명 인물의 선택지와 자유 입력을 번갈아 사용했다. 탐험가의 신문·
  도구, 노인의 외형 증언, 청소원의 승차권, 승무원 의뢰까지 정상 진행했다.
- 첫 실제 검증에서 “찾아 읽은 보고서를 보여드리겠습니다”가 제시 대신 열람으로
  보정되는 오류를 발견했다. `present` 의도를 보존하도록 고치고 재현 검사를 추가했다.
- 해당 턴 이전에 실제 플레이로 얻은 임시 기록에서 재검증했다. 보고서 전달,
  기관실 진입, 연도 증거 확인, 질문별 후속 응답, ‘아지산’ 정답 GOOD까지 통과했다.
- 후속 실제 검증은 38회 모델 호출·216개 검사 전부 통과했다. 가정·거절,
  증언 전 승차권 요구, 독립적인 부분 외형 답변, 다른 소유자의 표,
  노인의 정차·도난 질문, 승무원 관찰 답변, 잡담 뒤 “네”의 경계를 확인했다.
- 검토 중 발견한 “수락하면 어떻게 되나요?”의 실제 수락 오판정도 수정했다.
  현재 선택지 ID가 있어도 실행이 아닌 질문·조건문이면 수락하지 않는 회귀 검사를 추가했다.

실제 검증 보고서는 `.local/live-scenario-qa/20261111T030055Z-fbbca9`와
`.local/live-scenario-qa/20261111T031104Z-6de5e0`에 보관한다. 첫 보고서의
실패 기록은 수정 원인을 추적할 수 있도록 그대로 남겼다. 후속 검증은
`tools.live_dialogue_parity_cases:run_followups`로 실행했으며, 기존의
임시 검증 보고서만 사용하고 사용자 저장 데이터는 사용하지 않았다.
